# Context Engine

A schema-driven cognitive architecture for domain-specific AI assistants.

> Generated by AI. Review before use.
> Red Hat Confidential

## What This Is

Context Engine is a portable framework that makes AI assistants intelligent about a specific domain. It provides the reasoning architecture (how the agent thinks), the knowledge structure (what the agent knows), and the governance model (what the agent is allowed to do). It runs inside any AI editor (Cursor, Claude Code) or deployment platform (Red Hat AI Factory, custom infrastructure).

It is not an AI model. It is not an infrastructure platform. It is the layer between the model and the domain that turns a general-purpose AI into a domain expert.

## Where It Runs

| Runtime | How |
|---------|-----|
| **Cursor** | Rules as `.cursor/rules/*.mdc`, knowledge as workspace files, tools via MCP |
| **Claude Code** | Rules as `CLAUDE.md`, knowledge as workspace files, tools via MCP |
| **Red Hat AI Factory** | Rules as agent system prompt, knowledge as Business-as-Code YAML, tools via registered MCP servers |
| **Any MCP-compatible editor** | Rules as the editor's instruction format, knowledge as files, tools via MCP |

The framework is files. The files work anywhere an AI agent can read them.

## The Architecture in One Paragraph

A user's request gets classified into an **archetype** (what kind of work), an **object type** (what it's about), and a **scope** (how big). The **routing registry** selects which platforms to check. The **knowledge hierarchy** tells the agent what "correct" looks like (**profiles**) and where to find documentation (**source registry**). Evidence is gathered through one of **four evidence patterns**. **Governance** controls what the agent is allowed to do. **Templates** shape the output. Corrections feed back into the knowledge layer through the **learning loop**.

## The 5-Phase Workflow (URAD-L)

Every request flows through five phases:

```
Understand --> Resolve --> Act --> Deliver --> Learn
    |              |          |         |          |
 Classify      Gather     Execute   Present    Capture
 the request   knowledge  the work  results    corrections
```

1. **Understand**: What does the user need? Classify archetype, object type, scope, urgency, role.
2. **Resolve**: What knowledge applies? Load domain index, topic index, profiles. Check which systems are required. Build the evidence frontier.
3. **Act**: Execute using platform connections (MCP tools, browser, local generation). Reads are autonomous. Writes require preview and confirmation.
4. **Deliver**: Present results for the user's role. Lead with the answer. Attribute sources. Link resources.
5. **Learn**: Did the user correct anything? Classify the gap, draft the fix, route the improvement.

## The 4 Evidence Patterns

Every task in the framework uses one of four gathering strategies:

| Pattern | Used For | How It Works |
|---------|---------|-------------|
| **Object Verification** | Troubleshoot, verify, commission, provision | Load the profile (what SHOULD be), query platforms (what IS), compare the gap |
| **Artifact Population** | Create tickets, drafts, checklists, reports | Load the template, identify sources per field, gather evidence, populate |
| **Context Assembly** | Meeting prep, status updates, briefings | Identify evidence expectations, query systems in priority order, synthesize |
| **Aggregate Analysis** | Fleet health, portfolio review, audits | Define the population and standard, query at scale, report exceptions |

## The Knowledge Hierarchy

Four levels, from broad to specific:

```
Level 1: Domain Indexes (references/domains/*.md)
    Entry points for each area of responsibility.
    "This is the AV domain. Here's what it covers, what tools apply, what docs exist."
    |
Level 2: Topic Indexes (references/topics/{domain}/*.md)
    Narrower slices within a domain.
    "This is the video conferencing topic. Here's what to compare, when to expand."
    |
Level 3: Profiles (references/object-profiles/*.yaml, composite-profiles/*.yaml)
    What "correct" or "healthy" looks like.
    "A healthy codec has these fields in the inventory, these records in DNS, this monitoring."
    |
Level 4: Platform References (references/*-reference.yaml)
    Specific facts, conventions, parameters for each platform.
    "Here's how Netbox naming works. Here's the ServiceNow field mapping."
```

## The Schemas

Every content type has a schema. Schemas define what each file MUST contain. They are the contracts that make the architecture enforceable.

**22 schemas** organized in three layers:

### Content Schemas (what the knowledge files look like)
- `domain-index` - Domain entry point files
- `topic-index` - Narrower topic slices
- `object-profile` - Single-object healthy state across platforms
- `configuration-profile` - Device-level internal settings
- `composite-profile` - Multi-object environment state
- `target-state` - Artifact validity + evidence expectations
- `platform-reference` - Platform-specific facts
- `source-entry` - Live document catalog entries

### Config Schemas (what the control files look like)
- `routing-entry` - The routing matrix
- `applicability-rule` - System applicability rules
- `tool-classification` - Tool governance tiers
- `role-definition` - Role definitions and permissions

### Runtime Schemas (what each workflow phase produces)
- `prompt-classification` - Output of Understand phase
- `resolution-plan` - Output of Resolve phase
- `action-preview` - Preview shown before writes
- `write-verification` - Post-write read-back verification
- `verification-summary` - Post-action verification
- `learning-record` - Divergence capture
- `decision-trace` - Full routing and execution trace
- `session-summary` - End-of-session aggregated reporting

## The Governance Model

Three tiers for every tool action:

| Tier | Rule | Example |
|------|------|---------|
| **Read** | Execute autonomously. No confirmation needed. | Query inventory, search email, check monitoring |
| **Write** | Preview required. User must confirm before execution. Verified after. | Create a record, draft an email, update a field |
| **Prohibited** | Never execute. Explain why, offer alternative. | Delete records, send emails, modify shared infrastructure |

## Getting Started

> See `docs/quickstart.md` for a 30-minute hands-on guide.

### Minimum Viable Instance

To get a working system, define:

| What | How Many | Files |
|------|----------|-------|
| Domains | 3-5 | `references/domains/*.md` |
| Object types | 3-5 | Listed in `config/routing/registry.yaml` |
| Archetypes | 5-8 | Listed in `config/routing/registry.yaml` |
| Object profiles | 1 per object type | `references/object-profiles/*.yaml` |
| Platform connections | 2-3 | Listed in `config/tool-classification.yaml` |
| Templates | 2-3 | `templates/*.md` |
| Source registry entries | 10-20 | `registry/sources/*.yaml` |
| Roles | 1-2 | `config/roles/*.yaml` |

### Step by Step

1. **Fork this repository**
2. **Define your domains** (your team's areas of responsibility)
3. **Define your object types** (the things you manage)
4. **Create object profiles** (what "healthy" or "correct" looks like for each)
5. **Register your platform connections** (MCP servers, APIs, browser targets)
6. **Populate the source registry** (where your team's live documents are)
7. **Create output templates** (for your most common structured outputs)
8. **Run `setup/validate.py`** to check all files against schemas
9. **Start using it** - the knowledge layer grows through the learning loop

## The Write Lifecycle

Every write operation follows a strict sequence. No shortcuts.

```
Preview --> User Confirms --> Execute --> Verify (read-back) --> Report
                                |              |
                                |         Failed? --> Stop, assess, offer rollback
                                |
                           Failed? --> Report error, do not proceed
```

This catches the #1 production failure in AI agents: reporting success when the action silently failed.

## Safety Boundaries

The framework includes five safety mechanisms that prevent runaway behavior:

| Boundary | What It Prevents |
|----------|-----------------|
| **Loop detection** | Agent repeating the same failing action indefinitely |
| **Scope boundary** | A simple question expanding into a site-wide audit |
| **Resource budget** | Unlimited writes or excessive API calls in one session |
| **Wall-clock check-in** | Silent hangs with no user-visible progress |
| **Rollback guidance** | Inconsistent state from partially completed multi-step writes |

These are defined in `governance.mdc` and enforced at runtime.

## Design Principles

1. **Routing-first**: Don't hardcode procedures. Classify the request, select the starting point, let the evidence guide the path.
2. **Profile-driven**: Define what correct looks like before checking what is. The gap between profile and reality is the diagnosis, the work, or the answer.
3. **Schema-enforced**: Every content type has a machine-checkable contract. Files that don't conform get rejected.
4. **Evidence-patterned**: Four universal gathering strategies cover every task type.
5. **Self-improving**: Corrections feed back into the knowledge layer. The system gets better through use.
6. **Infrastructure-independent**: Runs anywhere an AI agent can read files and call tools.
7. **Data separated from behavior**: Rules contain only behavioral instructions. Reference data lives in config files loaded on demand.
